# 009 - 托管宿主路线可行性分析（能否「自己写个模拟器」跑原版游戏）

> 结论基于对原版 PE 的 CLI 元数据静态解析，非推测。全部脚本在 `tools/`，原始输出在
> `docs/evidence/spike_hostfeasibility.txt` 与 `docs/evidence/spike_icall_closure.txt`。

## 一句话结论

**可以，但不是写 PowerPC 模拟器，而是写「托管宿主」（managed host）**：
直接加载原版 `Assembly - CSharp.dll`（759 个游戏方法，100% 标准 CIL），
只用 C# 重写 UnityEngine 的原生核 —— 实测游戏真正触达的只有 **235 个 icall**。

这比现在的 Three.js 复刻优在：**游戏逻辑是原版二进制，行为必然 100% 一致**，
不存在「照着 IL 重写导致手感/判定偏差」的问题。

## 为什么 TigerOS / QEMU 必然卡

| 层 | 事实 |
|---|---|
| 目标码 | `Contents/MacOS/GooBall` = **12.7 MB PowerPC Mach-O** |
| 图形 | 走 Mac 原生 OpenGL Framework，QEMU 无 GPU 转发 → 软件光栅 |
| 结果 | 每帧软件渲染 + PowerPC 动态翻译，个位数 FPS |

自己写 PowerPC 模拟器不解决问题：瓶颈在**图形后端**，不在 CPU 翻译。
（类比：模拟 PS2 能跑但出不了画，瓶颈是 GPU 管线。）

## 决定性证据：依赖分层

```
GooBall.app/Contents/
├── MacOS/GooBall              12.7 MB  ← PowerPC 原生播放器（引擎核 + Mono 运行时 + 渲染）
├── Data/Assembly - CSharp.dll   148 KB  ← ★ 游戏逻辑：纯托管 IL
└── Resources/UnityEngine.dll    165 KB  ← 引擎 API：63.9% 托管 + 36.1% icall
```

### 证据 1：游戏逻辑零原生依赖

```
Assembly - CSharp.dll
  TypeDef=143   MethodDef=759   Field=1089   MemberRef=410
  InternalCall=0    PInvoke=0
  → 759/759 方法体是标准 CIL，任何 .NET 运行时可直接执行
  → 引用程序集仅 2 个: UnityEngine 0.0.0.0 + mscorlib 1.0.5000.0
```

mscorlib 1.0.5000 → .NET 4.x 只需一条 bindingRedirect（本机
`C:\Windows\Microsoft.NET\Framework64\v4.0.30319\` 自带，零安装成本）。

### 证据 2：UnityEngine.dll 一分为二

```
UnityEngine.dll
  MethodDef=2570
  纯托管     1641 (63.9%)   ← Boo 语言生成的高层包装
  InternalCall 929 (36.1%)   ← 方法体在 12.7MB Mach-O 里
```

Unity 1.x 的典型形态：**公开 API 全是托管包装，icall 藏在 `Internal_*` 叶子里**。

```csharp
// 托管层（可原样复用）
public Component GetComponent(Type type) {
    return Internal_CUSTOM_GetComponent(type);   // ← 这里才进原生
}
// Vector3.Distance / Dot / Cross / op_Addition 同理，全是托管 CIL
```

### 证据 3：游戏可达的 icall 闭包只有 235 个

从游戏逻辑引用的 316 个 UnityEngine 成员出发，沿托管包装向下做 BFS 传递闭包：

| 指标 | 数值 |
|---|---|
| 游戏引用的 UnityEngine 成员 | 330（去重归一） |
| 闭包触达的 UnityEngine 方法 | 569（最大深度 3 层） |
| **其中 icall —— 宿主必须重写** | **235** |
| 游戏不可达的 icall —— 可后置 | 694 / 929 |

**宿主只需实现全库 icall 的 25%。** 剩下的 `WheelCollider` / `CharacterJoint` /
`ParticleAnimator` / `WWW` / `GUIText` / `HingeJoint` 等原版单机流程根本不碰。

icall 工作面 TOP（完整 235 个清单见 `evidence/spike_icall_closure.txt`）：

| 类型 | icall 数 | 代表成员 |
|---|---|---|
| `GameObject` | 20 | `Internal_CUSTOM_GetComponent` / `SendMessage` / `AddComponent` |
| `Transform` | 17 | `Internal_GetLocalToWorldMatrix` / `Internal_GetPosition` |
| `Camera` | 16 | `Internal_CUSTOM_ViewportToWorldPoint` / `Internal_GetProjectionMatrix` |
| `Component` | 16 | `Internal_CUSTOM_SendMessage` / `Internal_Get_Custom_Prop*` |
| `GL` | 11 | `Internal_BeginCustom` / `Internal_LoadOrthoCustom` |
| `Input` | 10 | `Internal_GetAxis` / `Internal_GetKey` / `Internal_GetMouseButton` |
| `Application` | 8 | `Internal_LoadLevelCustom` / `Internal_IsPanther` |
| `GooLattice` | 8 | `Internal_AddForce` / `Internal_SET_DATAPROP_topSize` |
| `Rigidbody` | 8 | `Internal_GetVelocity` / `Internal_CUSTOM_AddForce` |

## 三条路线对比

| | A. QEMU/TigerOS | B. Three.js 复刻（现状） | C. 托管宿主（本报告） |
|---|---|---|---|
| 游戏逻辑来源 | 原版 Mach-O | **照 IL 重写** | **原版 DLL 原封不动** |
| 行为一致性 | 完美 | 可能偏差（手感/判定/关卡逻辑） | 完美 |
| 性能 | 个位数 FPS | 60 FPS | 60 FPS（原生 x64） |
| 依赖 | Mac OS X 10.4 完整系统 | 浏览器 | .NET Framework 4.x（本机自带） |
| 工作量 | — | 已完成 ~80% | 宿主层 ~1500 行 C# + 235 icall |
| 主要风险 | 无解 | 逻辑偏差累积 | `GooLattice` 等私有物理类语义需反推 |

## 实施路线（C 方案）

```
阶段 1  最小可跑 spike（目标：Lagoon 一关能跑）
  ├─ 建 CLR 宿主 exe（.NET 4.x，bindingRedirect mscorlib）
  ├─ 反射加载 Assembly - CSharp.dll + Boo.Lang.dll
  ├─ 实现 60 个类型的对象模型（GameObject/Transform/Component 生命周期）
  ├─ 实现首发必需的 icall 子集：Transform 17 + GameObject 20 + Time 7 + Input 10
  └─ 后端：先 stdout 打印调用序列（验证逻辑跑通），再接渲染

阶段 2  接入已出土资产（无需重解析）
  ├─ 复用 tools/unity1x.py 的 level4 解析结果直接建场景图
  ├─ 复用 assets/meshes + assets/textures（OBJ/PNG，218 张已全解出）
  └─ 后端换 Three.js（本地 8143 服务，与现有 game/ 共用资产目录）

阶段 3  补齐物理
  ├─ Rigidbody 8 + Collider 3 + GooLattice 8 + GooballCollider 1 + Tilter 1
  └─ GooLattice 是 Unity 1.x 私有「点阵物理」，从 BallController 的
     AddForce/SetUpVector/elasticity/snapBack 调用点反推语义
```

## 已验证的关键技术点

1. **IL 确实可被现代运行时执行** —— `csc.exe` 被沙箱策略拦截，改用
   `PowerShell [Reflection.Assembly]::ReflectionOnlyLoadFrom` 验证：
   `Assembly - CSharp.dll` 与 `UnityEngine.dll` 都能被 .NET Framework 4.x
   反射加载并读出 `Refs: UnityEngine 0.0.0.0 | mscorlib 1.0.5000.0`。
2. **元数据自解析可行** —— 无需 dnlib/cecil，纯 Python 按 ECMA-335 列模式算行宽，
   可读出 TypeDef / MethodDef / MemberRef / AssemblyRef。校验锚点：
   `TypeDef=143 MethodDef=759 Field=1089` 与既有 `dump_syms.py` 输出完全一致。
3. **方法体 RVA 映射正确** —— `GameObject::GetComponent` RVA=0x2e8c，
   首字节 `22 02 03 28 10 01 00 06` = `ldarg.0; ldarg.1; call MethodDef#0x110`，
   而 `MethodDef#272 = Internal_CUSTOM_GetComponent`（ImplFlags=0x1000 icall）。
   证实「公开 API 是托管包装、icall 在叶子」的结构判断。
4. **踩坑记录**：`MethodImplAttributes.InternalCall` 掩码是 **`0x1000`**，
   不是 `0x0001`（后者是 `IL`/`Managed` 标志位）。第一次统计得出「icall=0」的
   错误结论，修正后才得到真实的 929 / 235。
5. **踩坑记录**：MemberRef 的 `Class` 是 3-bit tag 的 coded index（tag=1 → TypeRef），
   MethodDef token 高字节是 `0x06`；初版 BFS 用 `__self__` 键导致内部调用全部失配、
   闭包恒为 0，改为按调用者 TypeDef 解析后才正确扩展到 569 个方法。

## 结论与建议

- **QEMU 路线是死的**（图形后端瓶颈），不必再投入。
- **Three.js 复刻继续做**（离可玩最近，且视觉已达标），但要意识到物理手感
  与关卡逻辑永远只是「近似」。
- **托管宿主是唯一能做到「原版行为 100% 一致」的路线**，且工作量已被
  235 这个数字证明是可控的。推荐在 Three.js 版达到「手感可接受」后，
  以托管宿主作为「原版精确模式」——两条路线共用同一批已出土资产。
